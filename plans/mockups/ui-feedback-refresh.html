Lumen UI refresh plan

Companion to plans/ui-feedback-refresh-plan.md, which is the plan of record. This page is an HTML approximation for discussion, not a pixel specification.

Lumen's layout, palette and feature set are in good shape. What's missing is response. Most controls look the same before, during and after a click, toggles barely show whether they're on, and the result of an action arrives as a line of small white text in the status bar. The app feels inert even when it's working. This plan fixes that first, then adds the at-a-glance cues and first-run polish that make an editor feel finished. No code has been changed yet.

Controls don't react

30 frameless buttons in 16 UI files, plus the activity bar, the title-bar toggles and Run/Stop, show no hover, pressed or keyboard-focus state.

On and off look alike

Panel toggles differ only by glyph color (#cccccc vs #a8a8a8). Disabled Stop stays red and disabled Apply stays blue, so they still look clickable.

Results whisper

218 code paths write to one 11px status line. At least 25 are errors, and they look exactly like successes. Messages never clear.

One set of states for every control

Every clickable thing should come from one of three shared widgets: a toolbar icon, a toggle and a text button. Each widget needs the same eight states. Today several of those states look identical, which is why a click goes unnoticed. The proposed column is the spec for the shared widget.

Findings and plan

Three phases, ordered by how much each one changes how the app feels. Phase 1 is what you asked about. File references are relative to src/ unless noted.

Phase 1

Make every click answer

Shared control states, visible toggles, progress for slow actions, and a feedback channel people notice. This is the part that makes the app feel responsive.

1

Icon buttons don't react to hover, press or keyboard focus

egui never paints a frame for a frame(false) button, and the theme gives idle, hovered and pressed widgets the same text color. The activity bar, panel toggles and Run/Stop force a transparent fill and a fixed glyph color, so they never change either.

Change: add one tool_button() to ui/widgets.rs with hover, pressed, on, busy, done, disabled and focus states drawn from new theme roles (control_hover, control_pressed, control_on). Migrate every icon button to it and keep widget IDs stable.

2

Toggles don't show whether they're on

The title-bar panel toggles are on or off only by glyph color, #cccccc against #a8a8a8 on a #3c3c3c strip. In the capture, the "on" left-sidebar toggle is indistinguishable from the two "off" ones.

Change: the "on" state becomes an accent-tinted chip with a 1px accent edge. Tooltips name the action ("Hide Left Sidebar" or "Show Left Sidebar"), and the accessible state reports selected. The same style applies to option toggles in Find, Problems filters and Settings scope.

Size Sui/task_launcher.rs:27-74ui/editor_find.rsui/problems.rs
3

Slow actions look like nothing happened

Commit, push, pull, fetch, clone, stash and refresh run on background threads and only set loading = true, which greys out the buttons. No "Pushing…" or "Committing…" text exists anywhere, and the UI has only three spinners (CSV, image and Markdown loading).

Change: the control that started the work shows a spinner and a verb ("Pushing…"). Anything over about 300 ms also gets a status-bar progress item. On success the control flashes a check for 1.2 s and then returns to idle. When there are commits to push, a visible Push button appears under Commit; Pull, Push and Fetch stay in the ⋯ menu as well.

Size Mapp/source_control.rs:259-267, 699-788ui/source_control.rs:914-983ui/source_control_menu.rs:27-35app/task_runs.rs
4

Results land in one easy-to-miss status line

218 code paths write view.status, and at least 25 of them are errors. Every message is the same 11px white text on blue, with no icon or severity, and it stays until something replaces it. "Opened 2 items from the command line" sat there for the whole capture session.

Change: replace the string with a small Notice { severity, text, action } model. Info and success messages show with an icon in the status bar and fade after about 5 s. Warnings and errors become a toast in the bottom-right that stays until dismissed and can carry an action (Show Output, Retry). A bell in the status bar keeps the history. Migrate the error messages first.

5

Text buttons look like labels

The theme sets the idle button fill to transparent, so "Open File", "Open Folder", "Details" and "Clone Repository…" read as plain text until hovered. The hover fill (#2b2b2b on #252526) is about 1.06:1, and the pressed and keyboard-focus states share the same look.

Change: add a secondary button fill (#3a3d41, hover #46494e, pressed #2c2f33) and keep the accent fill for the one primary action. Links that should read as text stay text-only, with an underline on hover.

6

Checkboxes and disabled controls are ambiguous

The checkbox box (#313131 on #1e1e1e) has no border, so an unchecked box nearly vanishes. Disabled controls keep their semantic color at half opacity: Apply stays blue and Stop stays red, so both still read as available.

Change: give checkboxes a 1px #6b6b6b border, with an accent fill when checked. Disabled controls use a neutral fill and muted text and never a faded semantic color, and they keep their disabled-reason tooltip.

Phase 2

Make state visible at a glance

Small, always-on cues that tell people where they are and what changed, without opening anything.

7

The editor lacks the cues that make it feel alive

There is no current-line highlight, the active line number looks like every other one, and there are no indent guides. The editor surface has no code for either (bracket matching exists).

Change: draw a subtle current-line band, a brighter active line number, and indent guides with the enclosing block's guide emphasized. Draw them from the same galley and viewport as the text, following the single-layout-authority rule in AGENTS.md. Add settings to turn each one off.

8

Nothing tells you something changed

The only activity-bar badge is the agent attention dot. Source Control shows no count of changed files and Problems shows no error count. In the Explorer, changed files get a status letter but their names keep the default color.

Change: add count badges on Source Control (changed files) and Problems (errors), using data that is already loaded, and tint changed file names with the same color as their Git letter.

9

Status bar items don't look clickable

Problems, Ln/Col and the language-server label are clickable, but they have no hover fill or pointer change. The Git branch and push/pull state don't appear outside the Source Control view.

Change: give clickable items a hover fill (white at 14%) and a pressed fill (22%). Add a branch item ("main ↑1") from the existing snapshot that opens Source Control when clicked.

Size Sui/chrome.rs:181-339
10

Tabs and pickers give little feedback

Inactive tabs have no hover state, and every tab draws its close × all the time, with no hover target under the ×. The command palette doesn't highlight which characters matched the query.

Change: add a tab hover fill. Show × on the active tab and on hover, and keep the dirty dot visible. Give × a hover square. Highlight matched characters in the palette and Quick Open.

Phase 3

First impression and finish

What a new user sees in the first minute, and the motion that makes the rest feel smooth.

11

The welcome screen undersells the app

The welcome screen shows a gray "LUMEN" wordmark, three text-only buttons and a hint line jammed underneath. It doesn't mention agents, Git, tasks or the terminal, and the app icon, which has a strong look, isn't used anywhere in the UI.

Change: show the app icon and name with a one-line description, a Start column (New Text File, Open File, Open Folder, Clone Repository), a Recent column, and four "get to know Lumen" entry points with their shortcuts. Every action is an existing command.

Size S–Mui/editor.rs:114-153ui/explorer.rs (empty state)assets/icons/lumen.png
12

Nothing moves

There are no transitions anywhere: hover fills, toggles and panels all snap. Combined with item 1, that makes the UI feel unresponsive.

Change: add 100–150 ms fades for hover and toggle fills, a short slide-in for toasts, a spinner for busy controls, and a pop when a badge count changes. Use ctx.animate_bool_with_time, which needs no new dependency. Add a reduce-motion setting.

Size S, after item 1ui/widgets.rscrates/settings-core/src/appearance.rs
13

Settings rows are noisy

Every row repeats "Live: true · Details · ⚙", and the full settings-file path sits above the list as a long line of text. The value metadata competes with the setting itself.

Change: show origin metadata only when a value differs from the default, reveal Details and the gear on row hover or focus, and move the file path behind a copyable "Open settings file" link.

New welcome screen, transitions with a reduce-motion setting, and Settings row cleanup.

Items 11, 12, 13

Each PR adds regression tests, following the existing render-level pattern of reading output.shapes: hover, pressed and on fills appear, disabled controls carry no semantic color, toasts persist for errors and expire for info. Each one also gets before/after captures at 900, 1280 and 1920 px in Dark, Light and High Contrast. The new roles need light and high-contrast values, and High Contrast relies on borders rather than fills.

What stays the same

  • Compact VS Code-style density, row heights, 5px pane corners and the 2px gutter.
  • The Dark palette values in AGENTS.md. New roles are added, and none are changed.
  • Native traffic lights and menus, the system UI font and the monospace editor font.
  • Command routing, document safety, dialogs and every existing workflow.
  • No gradients, no floating cards and no new permanent toolbars.

Decisions I need from you

  1. Toggle "on" styleI recommend an accent-tinted chip (shown in the mock). The alternative is a neutral gray chip, which is quieter but easier to miss.
  2. When to use toastsI recommend errors and anything that needs a decision only. Routine successes stay in the status bar and fade out.
  3. Tab close buttonI recommend showing × on the active tab and on hover, as VS Code does. Today every tab shows it.
  4. Status-bar branch itemThis is a small new item. Say yes if you want branch and push state visible outside Source Control.
How this was reviewed

I read the shared theme and widgets, the activity bar, title strip, launcher, status bar, Explorer, tabs, editor group, Source Control, Settings and chat code, and checked egui 0.33.3's button rendering to confirm the missing states. I compared against the earlier plans in plans/ui-enhancement-review.md and plans/ui-ux-visual-improvement-plan.md and left out what they already finished. Captures come from the app's own debug capture on macOS. Light and High Contrast themes, Windows and screen readers were not checked for this review.
